# Бэк 0.4.0 / поставка v10

## Сохранение и чтение

Room schema 3, миграции 1→2→3. Добавлены две служебные таблицы: vocabulary (оси, метрики, единицы) и store_generation (монотонное поколение сохранённого графа). Предметные ID, история и каталог не меняются. Миграция переносит словари из прежней metadata, не пересоздавая пользовательские строки.

RoomStore проверяет короткое поколение внутри транзакции и повторно использует прочитанный граф, пока оно не изменилось. Другая RoomStore, импорт или восстановление изменяют поколение, поэтому старый кеш не используется. После ошибки записи кеш сбрасывается. Холодное чтение/смена поколения всё ещё загружают граф целиком; это сознательная граница текущего компактного хранилища. Только RoomStore должен изменять базу, прямой SQL из UI не поддерживается.

Мутация сравнивает ID, значение и позицию строк. Неизменившиеся строки не сериализуются и не пишутся; изменённые записываются через Upsert и проверяются чтением обратно, удаления также проверяются. Session не использует SQLite REPLACE, чтобы не удалять сегменты каскадом. Удаление сессии выполняется после удаления/переноса её сегментов; закрытые сегменты сохраняются до нового открытого. Вся команда остаётся одной транзакцией. Полное восстановление проходит тот же механизм сравнения, включая удаления.

Проверка дерева использует один индекс на словарь вместо повторного построения для каждого узла. Поиск затронутых сессий сравнивает индексированные записи. Валидация всего графа пока остаётся на границе мутации: история не получила отдельного пагинированного SQL-движка, долгосрочная производительность на телефоне не измерялась.

## API будущего UI

`Tracker.views: Flow<TrackerView>` выдаёт согласованные ревизии. `Tracker.view()` — однократное чтение. `view.data` — сохранённый снимок, его коллекции нельзя мутировать. `view.snapshot()` пересчитывает только текущую сессию по Clock: нет обращения к хранилищу, сканирования всей истории или записи секунд. После следующего emission UI заменяет view; команды по старому token отклоняются. `view.report(...)` / `view.day(...)` явно рассчитывают отчёт по этой ревизии. Для preview графа/формы по-прежнему есть previewCorrection/applyCorrection. `tracker.canUndo(token)` сообщает о доступной одношаговой отмене; сама команда всё равно проверяет актуальность token.

Оболочка подписывается только в onStart и отменяет наблюдение/тикер в onStop. В фоне и при остановленном/приостановленном таймере секундного цикла нет. На каждом изменении ревизии или возвращении на экран рассчитывается отчёт; его время расчёта явно показано. Во время текущего таймера каждую секунду меняется только timer snapshot. Это техническая оболочка, не новый продуктовый дизайн.

Публикация Undo после транзакции сериализована с командами того же Tracker. Неудачная запись не публикует новую Undo. Архивная карточка теперь проверяется и в switchedEarlier, как в обычном Switch. Start оболочки передаёт заметку. Экспорт JSON захватывает Dataset и Moment в короткой транзакции, а сериализация/проверка копии выполняются после её окончания.

## Внешняя история

`HistoryTransfer.parseToggl(csv, namespace, zone, datePattern)` поддерживает подтверждённый набор колонок time-entry CSV Toggl: Project, Client, Description, Start date/time, Duration, необязательные парные End date/time. Формат длительности данного preset — H:mm:ss; календарный формат и исходная зона задаются явно. При наличии конца он сверяется с длительностью. Это не адаптер summary/grouped report или произвольного локализованного экспорта.

Основание: официальные [колонки CSV](https://support.toggl.com/en-us/article/editing-and-uploading-a-csv-file-bk155h/), [правила импорта и повторного detailed export](https://support.toggl.com/en-us/article/toggl-track-csv-import-guide-yx49tl/), [экспорт time entries через Detailed Report](https://support.toggl.com/en-us/article/exporting-data-z53uki/). Проверены локальные синтетические фикстуры по этим полям; фактический личный экспорт пользователя не предоставлялся.

`parseCsv(text, CsvMapping(...))` — общий независимый механизм для других трекеров: явные имена колонок, delimiter, ID, деятельность/категория/заметка, начало/конец либо длительность. Поддерживаются H:mm:ss, точные decimal hours, seconds и milliseconds. UTF-8 текст до 10 MiB, 50 000 строк и 128 колонок; BOM, кавычки, запятые, CRLF, переносы строки внутри поля. Повторные/пустые заголовки, повреждённые кавычки, недостающие колонки и неверные интервалы не угадываются.

Тimestamps без локального шаблона требуют ISO-8601 с offset. Локальный шаблон использует заданную IANA-зону; неоднозначный час DST и несуществующее местное время отклоняются. Нужно исправить источник или предоставить offset. Точность — миллисекунды, без скрытого округления. Portable-профиль допускает сохранённое ядром расхождение монотонной длительности и календарных границ до 1000 ms; остальные профили по умолчанию требуют точного совпадения.

`file.activities` показывает пары занятие/категория. UI передаёт явную `Map<SourceActivity, Classification>` в `transfer.preview(file, mapping)`. Можно выбрать имеющийся тип, карточку или неуточнённую Classification; карточки не создаются автоматически. Preview показывает интервалы, ошибки, предупреждения, число новых и повторных записей. Ошибка любой строки/пересечение/неверное сопоставление блокирует весь Apply. Проверяется также пригодность результата для полного backup, чтобы импорт не создавал неэкспортируемую базу.

AndroidRuntime предоставляет готовый `historyTransfer` с тем же приватным rollback-хранилищем, что и полный backup.

`transfer.apply(preview)` проверяет token, сохраняет и читает откатную копию, затем добавляет историю через одну команду Tracker. Неудача записи откатывает всё; устаревший preview требует нового просмотра. Доступна обычная Undo и долговечная JSON-копия. Повтор без новых записей ничего не пишет и не создаёт лишней rollback-копии.

Namespace должен постоянно обозначать один источник/аккаунт/workspace. При наличии внешнего ID ключ — namespace + ID; иначе — fingerprint исходных полей. Повторные строки/перестановка файла не удваивают историю. Тот же ID с изменёнными полями/интервалом/зоной даёт конфликт. Без ID изменённая исходная строка не может надёжно распознаваться как прежняя: пересечение блокирует импорт, а непересекающееся исправление пользователь обязан проверить. Это не синхронизация и не автоматическое слияние редакций.

Session.importOrigin содержит namespace, ключ, хеш строки/файла, зону и все исходные колонки. Заметка сохраняется отдельно. Tags, Client, Task, Billable и другие поля не теряются как источник, но не превращаются по догадке в локальные метрики/оси/финансовые сущности. Происхождение сохраняется при коррекции истории и в backup; Repeat создаёт новую обычную сессию без чужой импортной идентичности.

`HistoryTransfer.export(dataset)` — отдельный переносимый CSV с одним завершённым интервалом на строку, UTC timestamps, точной длительностью, заметкой и JSON контекста классификации/происхождения. Возвращает предупреждения об исключённых открытых/неопределённых/нулевых интервалах. Паузы/группировка в сессии и измерения не переносятся семантически через этот CSV — для полной точности нужен backup. Машинный CSV сохраняет текст точно; формулы таблиц не экранируются. Для анализа в таблицах остаётся прежний безопасный `Csv.export`.

Полный JSON теперь format 4; reader принимает 1/2/3/4. Добавлено только необязательное происхождение сессии, старые записи читаются без него. Reader старой версии приложения не обязан понимать новую копию.

## Точный остаток

Специализированный Simple Time Tracker adapter не заявлен: публичный репозиторий определён, но получить проверенный код/пример его конкретного CSV не удалось (GitHub tree API: 403; страница исходного каталога в web: restricted URL). Запрет не обходился. Для подтверждённого файла можно уже использовать общий CsvMapping; до заявления автоматической совместимости нужен реальный экспорт/исходная спецификация. Календарные колонки/локализация/длительность не угаданы.

Нет устройства, проверки батареи, многолетнего stress-теста, продуктового UI переноса, фонового сервиса или сетевой синхронизации. Lifecycle Activity/SAF на устройстве остаётся отдельной проверкой. Успешные JVM/Room сценарии не означают отсутствие всех дефектов.
