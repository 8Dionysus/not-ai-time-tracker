# Интервалы Focus

Focus — необязательные интервалы работы и перерыва. Перерыв не считается временем занятия. Поддержаны countdown, pause/resume/skip/cancel и явное восстановление. Длинные перерывы по циклам, task-provider, музыка, DND, автоматический запуск и награды отсутствуют.

## Один учёт

Focus использует одну обычную Session с обычными Segment. Каждый рабочий участок попадает в историю, Reports, CSV и Goals ровно один раз. Пауза и перерыв не имеют рабочих сегментов. Все рабочие фазы одного запуска Focus принадлежат одной логической сессии: цель по числу занятий не умножается от количества фаз/пауз.

Открытый рабочий сегмент имеет `limitMs` — оставшуюся длительность текущей фазы. Общий `materialize`, используемый таймером/отчётами/экспортом, ограничивает измерение этим бюджетом. После нуля время ожидания не становится работой. При явном переходе сегмент закрывается на доказанной границе, а перерыв начинается в момент команды, не задним числом. Следующая работа всегда запускается явным `focusNext`/`focusSkip`; пропущенные циклы не достраиваются.

Нет второго расходящегося счётчика истории. Work countdown выводится из тех же ID сегментов текущей фазы. Только break имеет отдельную временную опору, поскольку он не является рабочей историей.

## API для интерфейса

Вызовы ниже перечисляют отдельные обработчики действий; каждый получает token показанного состояния. Это не последовательный скрипт с одним token на все команды.

```kotlin
tracker.configureFocus(token, FocusPlan(workMs = 25*60_000L, breakMs = 5*60_000L))
tracker.startFocus(nextToken, classification) // либо явный plan только для этого запуска
val view = tracker.view()
val focus = view.snapshot().focus // null, если Focus не запущен
tracker.pauseFocus(token)
tracker.resumeFocus(token)
tracker.focusNext(token) // только DUE
tracker.focusSkip(token) // явный ранний переход, учитывает только прошедшую работу
tracker.cancelFocus(token) // завершает текущую сессию, сохраняет уже измеренную работу
```

Всё проходит через Tracker/StateStore и ожидаемый token; устаревшие действия не повторяются с новым token. Нельзя начать Focus поверх текущей обычной сессии или другого Focus. Сначала явный Stop/Switch сценарий пользователя; второй активный таймер не создаётся.

Обычные Pause/Resume/Stop/Switch автоматически используют правила Focus, когда он активен. Stop эквивалентен cancel; Switch атомарно завершает Focus и начинает обычное занятие. Старые Android-поверхности поэтому не открывают неограниченный рабочий хвост на перерыве. Для DUE/RECOVERY их первичная кнопка ведёт к приложению. Focus actions дополнены отдельным контрактом; экран/сигнал должен вызывать реальные команды, а не менять строки БД.

Поздняя разметка работает через `labelCurrent`. `changeDetails` разделяет текущую рабочую фазу с тем же оставшимся бюджетом; во время перерыва выбирает классификацию следующего участка. Исправлять длительности сегментов ещё текущей рабочей фазы нельзя: сначала закончить фазу или Focus. Прошлые фазы/сессии исправляются обычными командами и Undo. Ретроспективный Switch требует сначала завершить Focus. Это явные ограничения минимального среза, а не молчаливый пересчёт countdown по исправленному прошлому.

Общий `settings(token, settings.copy(focusPlan=...))` меняет только defaults следующих запусков; он намеренно не изменяет `FocusRun.plan` активного Focus. Для изменения его следующих фаз используется отдельный `configureFocus`; эта разница проверяется в интегрированном сценарии.

`configureFocus` меняет сохранённые defaults и параметры следующих фаз активного запуска. Текущая фаза сохраняет `durationMs`, включая паузы; введённая новая длительность не обнуляет и не переинтерпретирует уже прошедшее время. Обе длительности положительные, целые миллисекунды в поддерживаемом диапазоне. Нулевой перерыв заменяется явным Skip, отдельной системой правил не моделируется.

## Состояния и сигнал

`Snapshot.focus` содержит id запуска, token, фазу WORK/BREAK, индекс фазы, RUNNING/PAUSED/DUE/RECOVERY, duration/elapsed/remaining, безопасную подпись и действия. `Snapshot` сохраняет состояние обычного учёта: на перерыве Session PAUSED, хотя Focus countdown может RUNNING. Для обновления countdown UI ориентируется на Focus state, не только на общий Mode.

При DUE есть устойчивый `signalKey = runId:phaseIndex`. Видимый consumer дедуплицирует его в памяти. Отдельный opt-in `Settings.surfaces.focusSignal` разрешает best-effort фоновое уведомление: inexact ELAPSED_REALTIME AlarmManager, фактический POST_NOTIFICATIONS и канал. Receiver повторно проверяет runId/phaseIndex и режим DUE; новая фаза автоматически не начинается. Ключи доставленных уведомлений сохраняются private preferences между процессами. Exact alarm permission, DND и управление музыкой не используются; Android/OEM могут задержать доставку.

## Время, процесс и восстановление

`Moment.processId` нужен только Focus: AndroidClock создаёт его один раз на процесс, изменения Activity его не меняют. Внедряемый Clock должен предоставить собственную стабильную идентичность текущего процесса; при её отсутствии Start/Resume Focus отклоняется. Обычные таймеры продолжают прежнюю same-boot монотонную семантику и не требуют этого поля.

Рабочий Focus anchor проверяется по boot, monotonic и согласованности wall clock. Новый процесс в той же загрузке продолжает незавершённую фазу, если опора остаётся валидной. Время ограничено оставшимся бюджетом одной фазы; длительное ожидание даёт DUE, а не новые фазы или рабочие сессии. Новая загрузка, откат monotonic или скачок wall clock требуют RECOVERY. Process ID сохраняется для совместимости, но его изменение само по себе не инвалидирует same-boot опору.

Так же восстанавливается running break: он не запускает следующую работу и не начисляет ей время. Уже paused Focus переносим: закрытые рабочие сегменты или накопленное время паузы перерыва остаются достоверными, Resume создаёт новую опору. Простое закрытие/открытие Room в том же живом процессе не считается гибелью процесса.

```kotlin
tracker.resolveFocus(token, explicitStart, explicitEnd) // явно подтвердить/исправить рабочий хвост
tracker.resolveFocus(token, null, null) // явно исключить неизвестный рабочий хвост / закончить неизвестный перерыв
```

Решение завершает запуск Focus; новый можно начать отдельно с сохранёнными параметрами. Для work работают те же проверки интервала/пересечений, что у resolveTail. У break нет рабочего хвоста, принимаются только null/null. Cancel/Next/Resume не обходят RECOVERY. Разрешение поддерживает одношаговый Undo; сам countdown не получает журнал всех команд. Switch и обычные исторические исправления сохраняют прежний Undo. UI должен явно показать смысл исключения хвоста перед соответствующей командой.

## Хранение, перенос и совместимость

SQL Room schema 4. `Dataset.focus`, `Settings.focusPlan`, процессная опора и ограничение открытого сегмента — дополнительные сериализованные поля существующих metadata/segment payload. При старом payload Focus отсутствует и используются defaults. Downgrade APK не поддерживается.

Полный JSON **7**, чтение **1–7**. Для v7 обязательны поля goals и focus (null допустим). Сохраняются параметры, состояние фаз, связи и измеренное время, но не рабочие monotonic/process anchors. Активная work/break фаза после переноса требует RECOVERY. Paused Focus может быть явно продолжен. Preview показывает unfinishedFocus отдельно от unfinishedTail: у перерыва нет открытого рабочего хвоста. Восстановление остаётся полной атомарной заменой с проверенной откатной копией, не merge.

Пример: [focus-example.json](../evidence/focus-v15/focus-example.json) — тестовый полный JSON с активным Focus для проверки RECOVERY, не личная история. Повреждённые ссылки/параметры/бюджеты отклоняются до замены. Перенос сохраняет каталоги, Goals и их связи.

## Фактическая проверка и пределы

Те же три интегрированных сценария × Memory и Room/Robolectric. Новый связный путь: обычный таймер → Focus → pause/reopen/resume → уточнение → истечение и длительное ожидание → break/pause/resume → новая длительность следующей фазы → skip → коррекция/Undo → Switch/Undo → cancel → новый процесс/boot/скачок часов → явное восстановление → paused/active JSON. Суммы проверяются через Goals и обычный snapshot; два счётчика истории не складываются. Проверяются отказ Clock без processId, повреждённый импорт, чтение настоящей v14-копии и безопасные действия Android-поверхностей после потери временной опоры.

Сохранённые результаты введения Focus: [verification.json](../evidence/focus-v15/verification.json). Текущие проверки — [VERIFICATION](VERIFICATION.md).

Android runtime предоставляет [FocusDueSignals](BACKEND_V13.md) для дедупликации DUE callback по signalKey. Видимый технический экран может показать безопасную подпись; перерывный countdown учитывается отдельно от общего Mode сессии. Consumer не запускает другую фазу и не создаёт второй таймер. Его память относится к процессу; отдельный FocusSignals хранит delivery keys и планирует inexact OS alarm только при opt-in/permission. Гарантированной доставки OEM или exact alarms нет.

Физическое устройство и OEM-поведение не проверены. Полный экран управления Focus остаётся задачей интерфейса.
