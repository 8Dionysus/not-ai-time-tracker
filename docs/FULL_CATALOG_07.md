# Полная исследовательская проекция: baseline, ISCO v2 и спорт 0.7

Исходная база `research/catalog.research.json` не изменена: 1584 исходные записи, 1587 узлов исследования, 1584 runtime-типа и 82 оси. Полные исправленные дополнения находятся в `research/projections/`; размеры и SHA-256 — в manifest.json. ISCO v2: 353 строки, 137 основных предложений, 18 отдельных компонентов, 12 семейств/обёрток, 159 типизированных отношений. Спорт: все 223 строки. Старые предварительные проекции не используются.

## Явный app-facing импорт

`runtime.catalogImports` использует [full-catalog-manifest.json](../core/src/main/resources/full-catalog-manifest.json), включённый в core resource: восемь заранее известных файлов, их размеры и SHA‑256. APK включает эти восемь исходников как `assets/research/…`; Gradle `bundleCatalogAssets` копирует только принятые файлы из Git без изменения байтов. `runtime.prepareBundledCatalog()` открывает комплект из APK. Для внешнего локального комплекта вызывающая сторона может передать opener; manifest и ожидаемые digests не берутся из недоверенного пакета. Reader закрывает streams, ограничивает каждый ввод объявленным размером плюс один контрольный байт и проверяет все восемь источников до подготовки плана.

```kotlin
val importer = runtime.catalogImports
val preview = runtime.prepareBundledCatalog() // на IO, не в main/ticker
// Альтернатива для локального комплекта из checkout:
// val preview = importer.prepare { path -> File(researchDirectory, path).inputStream() }
// Показать preview.types, preview.axes и preview.report.entries; отмена ничего не пишет.
if (preview.canApply) importer.apply(preview) // только после явного подтверждения
```

`FullCatalogImports.sources` сообщает канонические относительные имена, размеры и хеши для формы выбора файлов. Это загрузка существующего принятого корпуса, без автоматического обновления, сетевого downloader или нового переносимого формата. Имена map не заменяют проверку bytes/hash. Исходники распространяются в [research/](../research/README.md) и включаются обычной сборкой `:app:assembleDebug` в APK. Для JVM/внешнего импорта получите checkout репозитория (`git clone https://github.com/8Dionysus/not-ai-time-tracker.git`) и передайте его каталог `research/` в opener выше; все восемь путей перечислены в manifest. После checkout файлы доступны локально; runtime не запрашивает сетевой или постоянный доступ. Условия повторного распространения проекта пока не выбраны. Создание runtime, первый запуск и подготовка preview ничего не импортируют; экран должен отдельно вызвать Apply после подтверждения.

Проверенная неизменяемая проекция может переиспользоваться между живыми previews через одну weak-reference; все входные файлы всё равно сверяются при каждом prepare. После освобождения previews source graph может быть собран GC. Импорт полного 28 MiB корпуса — отдельная IO-операция, а не часть Start/ticker; память/скорость на телефоне не измерены.

Preview фиксирует token и все конфликты. Отсутствующий companion, wrong hash, конфликт и stale token не изменяют Dataset. Apply сохраняет и проверяет исходники в app-private `noBackupFilesDir/research`, затем одним `addCatalog(..., rejectConflicts=true)` устанавливает пакет. Повторный импорт не добавляет дубликаты. Если состояние изменилось после preview, требуется новый preview. Успешно архивированный неизменяемый источник может остаться после отказа транзакции.

Установка остаётся явной: первый Start без карточки и пять bootstrap-типов не запускают импорт. Пользовательские имена/связи не перезаписываются; конфликт требует отдельного решения пользователя.

## Вызов ядра

`FullResearchCatalog.read(basePlan, iscoBytes, iscoSha256, sportsBytes, sportsSha256)` возвращает полный `FullResearchPlan`, без top-N и скрытого отбора. `basePlan` получается существующим ResearchCatalog с пятью supporting-документами (см. RESEARCH_FOLLOWUP.md). Перед подготовкой FullResearchCatalog проверяет закреплённый SHA-256 baseline и наличие всех пяти supportingHashes; ResearchCatalog.read уже проверяет байты предоставленных companions. Другой корректный ResearchPlan или отсутствие одного companion отклоняются с UNSUPPORTED_IMPORT до получения плана и любых записей. Это низкоуровневая граница: вызывающая сторона обязана брать ожидаемые digests из доверенного manifest, а не вычислять их из самого входа. App-facing FullCatalogImports выполняет эти проверки и загрузку всех supporting inputs.

`plan.vocabulary`: 1918 типов и 337 осей. `plan.outcomes`: JSON pointer, исходный ключ, вид решения, runtimeIds и точная граница преобразования. `plan.sourceBytes(file)` отдаёт оригинал. `plan.apply(tracker, currentToken, privateArchive)` сохраняет и проверяет полный корпус и supporting-документы, затем вызывает один транзакционный `Tracker.addCatalog`. Возвращает обычный Change с catalogImport (ADDED/UNCHANGED/CONFLICT). Повторный импорт не добавляет дубликатов; локальные определения не перезаписываются. По умолчанию низкоуровневый apply сохраняет частичную семантику addCatalog; package importer использует rejectConflicts=true для атомарного отказа любого конфликта. Устаревший token, невалидные ссылки и ошибка архивирования оставляют базу прежней. Архивный файл после отказа транзакции может остаться как неизменяемое доказательство.

Все baseline-типы остаются равны прежним определениям, включая родителей и provenance. Для новых типов сохраняются явно заданные исходником parentId. При отсутствии рекомендации родителя тип остаётся корневым: соседство, роль, частичное пересечение и сходное имя не становятся иерархией. Неявные ISCO root-placement удалены: boundedDefinition и frozen source decision не разрешают создавать тип. 28 явно предложенных спортивных целых не имеют заданного родителя. Это видимая граница источника, а не потеря занятия.

## Целое занятие и части

28 спортивных whole-event/family записей и девять выбираемых профессиональных семейств запускаются обычным `Tracker.start(token, tracker.typeSelection(id))`, без обязательных уточнений. Исправленное selectionAndCountingRule имеет приоритет над историческим selectableActivityType=false у 14 спортивных записей; исходный флаг не переписан. Части доступны отдельно, а связи не создают сегменты или дополнительные минуты. Для смены фактического занятия используется Switch; смена уточнения текущего — changeDetails. Repeat сохраняет классификацию, но не копирует измеренный результат. Одновременный второй таймер не вводился.

ISCO: только прямые отношения с явным mergeEligible могут связывать дубль с одной рабочей записью. Транзитивное объединение всего кластера, слияние по названию, поглощение частичного пересечения запрещены. Исходные определения каждой стороны сохраняются. 137 явных основных предложений и 18 компонентов доступны в runtime. Четыре residual-предложения без принятого отображения остаются открытыми в источнике и outcomes; residualId не используется как runtime ID. Три из них ошибочно создавались напрямую, а photosensitive_media_manufacture ссылался на теперь исключённый fallback. Единственный residual с принятым отображением — animal_equipment_tack_cleaning. У retired/split/context wrappers отсутствие whole mapping явно помечено: ссылки на компоненты не объявляются полной эквивалентностью.

37 спортивных уточнений и исходные role/context/stage поля представлены необязательными осями. Значения с устойчивыми исходными ID — LOCAL_CHOICE; примеры без ID — FREE_LABEL. Это не обязательная форма и не вывод значения из названия. Для baseline-hosts привязки новых спортивных осей остаются в companion outcomes, чтобы не создавать конфликт изменением ранее принятого словаря.

## Сохранённый остаток

Все разделы обоих оригиналов сохранены целиком, включая provenance, определения, pair decisions, исторические aliases, предупреждения ложных слияний, HETUS, semanticCorrections и ограничения источников. Они не превращены в универсальный движок отношений. Порядок частей, вариативные составы (включая tetrathlon 4 из 5), роль/контекст и связи компонент доступны в оригиналах; runtime не придумывает для них правила, доли времени или обязательность. Только `arisf:arISF_075` / wheelchair American football IFAF не имеет типа занятия: конкретный пробел правил источника сохранён; остальные спортивные строки не заблокированы.

JSON backup 7 (reader 1–7) содержит полный рабочий словарь, origins, пользовательские данные и настройки; исследовательские документы переносятся отдельными неизменяемыми companions. Не увеличивали лимит 10 MiB и не встраивали 25+ MiB исходников в пользовательский backup. Room schema — 3. Полный каталог вызывается через описанную явную границу; [runtime-vocabulary.json](../evidence/full-projection/runtime-vocabulary.json) сохраняет результат исторической проекции для сравнения. Это не обещание автоматической переклассификации существующей истории.

## Проверка и артефакты

Полная проекция встроена в прежний интеграционный сценарий smallHistoryAndExport, отдельно на Memory и Room/Robolectric. Проверяются все исходные строки, точные байты, неизменность baseline, целостность ссылок, полный импорт/повтор/конфликт/устаревший token, 37 стартов целого без деталей, Repeat, отсутствие дополнительных сегментов, сохранность истории, полный JSON round-trip и отказ при повреждении. Остальные два сценария и прежние quantity-проверки сохранены. Текущие результаты — [VERIFICATION](VERIFICATION.md); исторические журналы и результаты проекции — [evidence/full-projection](../evidence/full-projection/summary.json). Проверка на устройстве не проводилась.

## История исправления проекции

Удалено создание типа из `isco.research.<recordKey>` при отсутствии proposedActions и точного reuse. Удалено создание трёх типов из residualId при runtimeIdAssigned=false. По сравнению с предварительной проекцией исключены 174 ошибочно созданных определения (171 fallback + 3 residual); исходные 353 строки ISCO, все связи, решения и исходники сохранены. Спортивная проекция и baseline сохранены без изменений. Набор новых ISCO ID в регрессии должен точно совпадать с 137 proposedActions + 18 componentActionProposals; ни один residualId или fallback-ID frozen-строки не допускается.

Полный исправленный словарь: 1584 baseline + 137 ISCO proposals + 18 ISCO components + 151 новых спортивных типов + 28 спортивных целых = 1918 типов; осей по-прежнему 337. Это уменьшает объём рабочего словаря без новых механизмов или дополнительных операций при работе таймера. Скорость на телефоне не измерялась.

Если предварительный каталог уже импортирован в пользовательскую базу, addCatalog намеренно не удаляет существующие типы и связанную историю. Исправление запрещает новые ошибочные добавления; автоматической очистки пользовательских данных нет. Способ установки на чистое состояние и явное полное восстановление остаются прежними.

## Авторские описания ISCO и совместимость установленного каталога

В текущем ISCO inputs 86 unit-reviews для 60 категорий, включая `projectionHistory`, используют `researchActionSummary`: самостоятельные предметные описания для решений каталога. 452 краткие candidate-level формулировки обозначены `researchTaskSummaryEn`; они не выдаются за официальные выдержки. `summaryProvenance.officialText=false` явно фиксирует роль описаний. Коды, названия категорий, страницы и ссылки на источники сохранены, как и action-level mappings, границы, решения и counts. Это исправление содержания, без выбора лицензии или утверждения полного clearance.

Изменились SHA и размер ISCO файла; оба manifests и test pin обновлены. Определения runtime остаются теми же: 1918 типов/337 осей, 353 ISCO dispositions, 137 proposals, 18 components, 12 families и 159 typed relations. Сравнение полной VocabularyData с предыдущим сохранённым словарём допускает только новую пару SHA в ISCO origins; все IDs, names, definitions, relations, versions, choices и прочие поля сравниваются точно.

При ранее установленном каталоге обычный `addCatalog` продолжает считать другой provenance конфликтом. Только проверенный package importer признаёт известную пару ISCO SHA `7dd02e40…` → `e7a9f50c…` описательной ревизией, когда все остальные поля определения и origin locators совпадают. Такое определение получает UNCHANGED; **старый installed provenance сохраняется**, чтобы точно указывать источник первоначального импорта. Новые определения получают текущий provenance; новый корпус архивируется при явном Apply. История и старые архивные источники не переписываются. Неизвестная версия, изменённый локатор, имя, смысл или пользовательская правка остаются конфликтом всего пакета.
