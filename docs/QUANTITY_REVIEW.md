# Количественные проекции исследовательских записей

Различаются четыре смысловых случая: `measure.gait_style` — категория, `measure.training_block` — метка/ссылка, посадки имеют самостоятельные дробные площадь и длину, а собранные ресурсы — дробные массу/объём наряду со счётом единиц/переносок. Исходники исследования не менялись.

Для каждой записи задана отдельная проекция; общей запасной ветки нет. `core/src/main/resources/research-quantity-projections.json` содержит явное решение для каждой из 71 исходных записей: определение, source-qualified pointer/ID, отдельные допустимые варианты и содержательный остаток. Этот один файл читают ядро и генератор `scripts/review_research.py`; представимость не выводится из общего `measureKind`. Решения привязаны к SHA-256 корпуса 0.5. Новый корпус требует пересмотра, а не молчаливого применения этих решений.

Всего 115 числовых вариантов по 64 исходным записям и 5 вариантов категорий/ссылок. Это число source-qualified вариантов, не число независимых глобальных величин: повторные определения и reuse не объединяются по названию. Два исключительно категориальных источника не принимаются числовым API. У пяти записей нет новой проекции: три упоминания длительности используют Segment, расписание требует task/schedule состояния, остаток продукта — object/location/snapshot состояния.

## Контракт вызова

`plan.quantityProjections()` возвращает решения с `variants`, их смыслом, типом, размерностью и `remainingGap`. Для 27 записей из work compatibility необходим проверенный supporting document; без него эти записи не рекламируются как проверенные.

`plan.quantityVocabulary(pointer, basisId, localId, meaningLabel, scope, unit, maxScale)` создаёт один Metric и явно выбранную UnitDefinition. `basisId` обязателен даже у одиночного варианта: отсутствующее/неизвестное основание — INVALID_INPUT. Размерность единицы должна соответствовать варианту. Для валюты используется `currency:USD` и аналогичный явный трёхбуквенный код; курсы не подставляются. `factorToBase` должен быть положительным, преобразование остаётся точным механизмом ядра. Для счёта используется собственная размерность основания, а не универсальная взаимозаменяемая штука. Целочисленные варианты не принимают дробные Measurement; масса, объём, площадь и длина — DECIMAL.

`meaningLabel` описывает конкретный пользовательский материал, статус, упражнение, текст/издание или шкалу. Новый `localId` отделяет другой смысл. Объект, получатель, место и другие личные сведения не обязательны для обычного таймера. Этот API не проверяет истинность свободного описания и не заменяет выбранный смысл выводом из имени занятия.

Пример независимой площади посадки:

```kotlin
val row = plan.quantityProjections().single {
    it.sourceId == "qneed.garden.planting_and_growing_quantity"
}
val vocabulary = plan.quantityVocabulary(
    pointer = row.pointer, basisId = "area", localId = "spring-bed",
    meaningLabel = "Площадь весенней посадки грядки",
    scope = Scope.SESSION,
    unit = UnitDefinition("local.square-metre", "м²", "area")
)
tracker.addCatalog(expectedToken, vocabulary)
// Measurement.value = Decimal("1.25") допустим; это не число растений.
```

`quantityFacetVocabulary(pointer, basisId, localId, kind, cardinality, values)` использует Axis для стиля, блока, маршрута и контейнера. FREE_LABEL сохраняет подпись; LOCAL_CHOICE — явно зарегистрированный локальный ID. Полноценной сущности маршрута/плана/контейнера это не создаёт. Числовое основание нельзя провести через этот метод, категорию нельзя провести через quantityVocabulary.

Установка — существующий `Tracker.addCatalog`; возвращается тот же per-ID конфликт вместо перезаписи личного. Исходные байты следует сохранить через `plan.apply` (пустой выбор допустим) в ResearchArchive. Каждая новая метрика/ось содержит ResearchOrigin; basis и source pointer участвуют в устойчивом ID. Новые factories не запускают таймер и не меняют историю.

## Границы представлений

Все числовые варианты — `BY_TARGET`, без автоматического SUM. Ручное число относится к целой SESSION или SEGMENT, а не к вырезке дня. Повтор появления session value в разных дневных отчётах сохраняет прежний контракт. Старые `measureVocabulary` и `scalarVocabulary` оставлены для совместимости; их ID не переписаны. Не следует устанавливать старое и новое определения как две записи одного факта.

- События, предметы, образцы, порции, поездки, ответы и результаты: можно ввести известный агрегат одного основания/статуса. Ядро не знает входящих event/object IDs и не обещает дедуп между сессиями. Planned/cancelled/attempted/completed различаются выбранным локальным определением.
- Пакет/упаковка: числовое содержимое одной указанной упаковки допустимо как BY_TARGET аннотация. Это не дополнительная покупка и не автоматическое умножение упаковок на объём. Recipe requirement — плановое количество выбранного ингредиента, не фактический расход и не рецепт-движок.
- Скорость и темп разделены по размерности. Движущееся/записанное время выбирается явно; автоматических средних, reciprocal conversion или значения при нулевом знаменателе нет.
- Страницы — объём чтения, не позиция или уникальное покрытие. Chapters/episodes требуют своей конвенции учёта частичного/повторного потребления. Текущую позицию можно аннотировать собственным BY_TARGET Metric через существующий API, но это не объектное состояние и не причина заявить завершение произведения.
- Score/rating: доступны только явно выбранные неотрицательные значения. Рейтинг не складывается, направление «лучше» не выводится; `maxScale` не проверяет границы шкалы. Signed score/handicap и изменение рейтинга не маскируются под положительный скаляр.
- Слова: gross additions, source translation, target translation и review exposures — четыре разных ручных основания. Review exposures явно считают проходы, не уникальное покрытие. Signed net delta и document snapshot/version/latest state остаются отдельными расширениями; положительное число не заменяет их полный смысл.
- Stock snapshot и recurrence/due-state: существующий `saveMetric` позволяет пользовательскую числовую аннотацию, но полное исследовательское определение требует состояния/времени/объекта, поэтому adapter не выдаёт её за готовую поддержку запасов или расписания.

Точные определения и индивидуальные ограничения всех 71 записей находятся в `evidence/research/followup-quantity-review.json`; исходные six word-count bases сохранены там целиком. Это не утверждение о реализации object/event/schema расширений.

## Проверка

Те же 3 Core и 3 Room/Robolectric сценария создают все 115 числовых вариантов, вводят реальные целые/дробные Measurement, проверяют отсутствие quantityTotals для BY_TARGET, происхождение через полный JSON restore, повторный импорт и конфликт с личным названием. Проверяются отказ для категориального числа, отсутствующего основания, неверной размерности и signed net-delta варианта. Стиль проходит реальный Start, Repeat и JSON; Repeat сессии с измерениями не создаёт новых результатов. Проверки legacy JSON, повреждений, размера и rollback входят в общий набор. Результаты — [VERIFICATION](VERIFICATION.md). Удобная форма ввода количеств и физическое устройство не проверены.
