# Проверка оставшейся семантики корпуса 0.5

Пять предоставленных оригиналов прочитаны через Library read API и сохранены в `research/supporting/`. API не вернул конечный LF: восстановление одного LF дало точное совпадение размера и SHA-256 каждого файла с manifest 0.5. Изменений исходных документов нет. Подробные размеры и хеши: `evidence/research/followup-summary.json`.

## Результат для ядра

`ResearchCatalog.read(bytes, hash, supportingDocuments)` принимает карту имени оригинала к байтам, проверяет каждый хеш по manifest. `plan.apply` сохраняет и проверяет чтение всех предоставленных оригиналов до изменения БД. Исходный вызов без карты остаётся доступен, но не заявляет проверку отсутствующих документов. Новые factories возвращают `VocabularyData`; установка проходит обычный `Tracker.addCatalog(token, vocabulary)` с сохранением локальных конфликтов. Для архивирования доказательств сначала вызвать `plan.apply` с нужным выбором (в том числе пустым).

- 82 из 102 осей доступны по явному выбору `axisCandidateIds`: исходные FREE_LABEL/LOCAL_CHOICE и кардинальность сохранены. Для leisure источник прямо допускает свободный текст и несколько значений — используются FREE_LABEL/MULTIPLE. Только явно заданные исходные `valueId` входят в стартовый реестр; строковые примеры не становятся закрытыми списками. Новое личное choice добавляется явно через `saveAxis`. Ни одна ось не обязательна.
- 17 work/learning предложений без `valueKind/cardinality` доступны через `configureAxis(inventory, sourceId, localId, kind, cardinality, values)`. Это явный выбор простой схемы с новым локальным ID, без миграции прошлого. Для описательных пересекающихся признаков рекомендуется MULTIPLE/FREE_LABEL; для стабильных ссылок и выбранных статусов — LOCAL_CHOICE. Универсальная нормализация не требуется для сохранения текста.
- Оставшиеся три оси: `work_learning/project` противоречиво требует `projectId`, объявляя free_label и смешивая проект/клиента; рекомендуется локальный реестр project IDs и отдельная ось клиента. `private_display` требует настроек карточки, а `observation_record_fields` — предметной записи. Их нельзя без потери смысла объявить обычными аналитическими фасетами. Соответствующая крупная модель не внедрена молча.
- `primarySupervisionVocabulary()` создаёт отдельный тип «Присмотр как основное занятие». Это явный основной Start на единственной временной шкале. Исходная параллельная ответственность сохранена, не переопределена. Родственный контекст выражается необязательной `life_care/relationship_private`; журнал моментальных событий остаётся отдельной моделью.
- `measureVocabulary(sourceFile, sourceId, localId, meaningLabel, scope)` поддерживает ограниченные ручные скаляры: distance, elevation_gain, sets, repetitions, pages. `pages` означает объём прочитанного, включая выбранное пользователем перечитывание, а не текущую позицию или уникальное покрытие книги. Источник и конкретный смысл остаются отдельными.
- `scalarVocabulary(sourceId, localId, meaningLabel, scope, maxScale)` для пяти доказанно представимых рабочих величин: length/area/volume/mass и число response attempts. Материал/операцию либо основу ответа задаёт вызывающая сторона в названии отдельного локального определения. Единицы m/m²/m³/kg/response, точное число, без автоматической суммы. Все новые скаляры `BY_TARGET`: значения всей сессии/сегмента не превращаются в дневной объём. Factory не обещает структурированного ID объекта/события.

`Metric.researchOrigins` необязателен, как origins у Axis/ActivityType. JSON остаётся формата 3; читатель 1/2/3, Room schema 2. Внешние документы не встраиваются в пользовательскую JSON-копию; они отдельно входят в поставку и evidence archive. Указатели `/supporting/<file>/...` разрешаются внутри проверенного оригинала, остальные — внутри основного пакета. Прежние поставки сохранены историей Git/Library.

## Поэлементные материалы

`evidence/research/followup-axis-review.json` содержит все 102 исходных определения, отмечает прежние 97, ограничения ядра, допустимое представление и конкретный остаток каждого. `followup-value-review.json` содержит все 760 вхождений, в том числе 73 compound_split и прочие составные/неоднозначные формы: точный оригинал, отдельные component proposals, их отношения и оставшуюся неоднозначность. Косая черта не означает ни автоматическое разделение, ни синонимию; целая подпись может сохраняться без потери написания, но не выдаётся за нормализованную классификацию. Эти файлы воспроизводятся `python3 scripts/review_research.py`.

`followup-quantity-review.json`: 20 исходных величин, 24 бытовых кандидата, 16 рабочих величин и 11 точных reuse-решений, отдельно шесть word-count bases. В каждой записи сохранены определение, scope, правило агрегации/контекст и конкретная граница. `followup-node-review.json` разбирает все три недлительностных узла.

Для будущего изменения модели предлагаются следующие ограниченные варианты:

| Потребность | Доступно сейчас | Рекомендованное отдельное расширение, если потребуется |
|---|---|---|
| Уникальные события/предметы, статус и этап | Явно известный агрегат SESSION/SEGMENT с отдельным metric ID/basis | Небольшая таблица record ID/type/status и ссылки на сессии; дедуп по record ID, не названию и не сегменту |
| Позиция, stock/document snapshot | Отдельное BY_TARGET число как аннотация сессии, без обещания состояния объекта | Object ID/version + timestamp/basis; выбор снимка, без SUM |
| Чистое изменение слов, возвраты | Отрицательное число отклоняется; gross/count остаются отдельными смыслами | Signed quantity с явным видом DELTA и базой/версией объекта; не разрешать отрицательные значения всем прежним метрикам |
| Шкала усилия, score/rating | Неотрицательный BY_TARGET скаляр с выбранным определением | Диапазон/шкала в версии метрики; не путать maxScale с min/max значения |
| Вес каждого подхода | Отдельные однозначные агрегаты, без структуры подходов | Set/event target только при реальном запросе на по-подходный учёт |
| Параллельная ответственность | Метка либо явно выбранный основной присмотр | Неаддитивный интервал ответственности отдельно от Segment; общий итог только по основной шкале |

Повтор значения всей сессии в разных дневных отчётах — намеренный контракт. Суммировать такие дневные строки между собой нельзя. Count, position, unique coverage и signed delta не взаимозаменяемы. Запланированное/отменённое событие не становится выполненным.

## Междоменные связи и mobile research

Проверены реальные 357 пар: уникальные ID/пары, квалифицированные исходные ссылки, оба уровня `recordScope/sourceRecord` и `normalizedActionRelation`, направления, определения, счётчики типов, обратные ссылки всех 239 life/care записей. Шесть identity-решений сверены с отдельным документом; три новые формулировки проверены точно. Даже normalized broader/narrower не становится parent-ребром. Исходный документ явно содержит `essentialActionDimensionsNotTreatedAsRemovedContext=false`: семантическое исследование не объявлено окончательно безупречным только потому, что структура прошла проверку.

Mobile документ — доказательства и гипотезы. Его 39 источников и 37 сценариев сохранены; UI, ранжирование, исправление опечаток, portable catalog envelope и тесты TalkBack/устройства не реализованы этим проходом. Текущий Favorite сохраняет Classification, Repeat дополнительно копирует note; предложения о Recent/item favorite/detail pin остаются отдельным продуктовым решением. Пользовательские значения не заменяются переводом или именем из исследования.

## Проверка

Те же три сценария Core и три Room/Robolectric проверяют полный корпус, вспомогательные хеши/отношения, реальные фасеты и сохранение исходных составных подписей, configured axis, основной присмотр, ручное измерение, повторный импорт/конфликт, JSON round-trip и архив каждого источника. Прежние проверки форматов 1/2/3 и rollback остаются. APK и lint собираются обычной командой из README; результаты находятся в evidence. Устройство/эмулятор не проверялись.

Исправление и расширение количественных представлений после приёмки v6: [QUANTITY_REVIEW.md](QUANTITY_REVIEW.md). Общая запасная формулировка удалена; 71 запись разобрана явно, категории не преобразуются в числа.
