# Каталог и ядро v3: проверка совместимости

11 октября 2026. Статический разбор переданного исходного кода, commit 6475637c74263fbc5bddcff73398372a1daa8e5e. Новых тестов и изменений кода в этой проверке нет. Источники: core/src/main/kotlin/dev/notai/tracker/Vocabulary.kt (весь файл), Model.kt (типы и Measurement), Reports.kt (формирование отчёта и количественные итоги), Tracker.kt (сохранение словарей и измерений). Это перечень входов для согласованной интеграции каталога, а не заявление о готовом адаптере.

## Уже поддерживается

- ActivityType: один parentId, aliases, definition, selectable, archived, suggestedAxisIds/suggestedMetricIds. Число узлов и глубина не зашиты. Можно выбирать широкую категорию, не заполняя уточнения.
- Classification фиксирует ancestorPathAtWrite. Изменение дерева не переписывает исторический путь; отчёт использует сохранённый путь.
- Axis: FREE_LABEL или LOCAL_CHOICE, SINGLE или MULTIPLE, версия смысла. Значения имеют ID, версию и архив. Свободный текст и закрытый справочник различаются. Новое локальное значение можно добавить в справочник через явное сохранение оси; нельзя отправить неизвестный valueId и считать его автоматически созданным.
- Фасетные срезы могут пересекаться. Общая длительность строится по уникальным сегментам; byType/byFacet нельзя складывать как независимые части целого.
- Metric: целое или десятичное неотрицательное значение, каноническая единица, точность, SESSION/SEGMENT, SUM/BY_TARGET. Значение сохраняется точной десятичной строкой.
- Подготовка конвертации возвращает исходный черновик и ошибку, если точное значение нельзя получить. Не выполняется незаметное округление.
- addCatalog возвращает результат для каждого ключа ADDED/UNCHANGED/CONFLICT. Новые записи добавляются, конфликтующие локальные сохраняются. CONFLICT означает, что предложенный каталог применён не целиком; это не атомарный отказ всех неконфликтных добавлений.

## Что адаптер обязан подготовить явно

1. Общее пространство ID. Исходные записи квалифицировать разделом, затем применить отдельные решения для шести конфликтов исходных action-ID. Совпадение строки ID между четырьмя исследовательскими источниками не доказывает одинаковый смысл.
2. ParentId — одно выбранное пользовательское дерево. Смысловые отношения «подтип», «этап», «пересечение» и дополнительные поисковые связи нельзя без разбора превращать в parentId. Они сохраняются отдельно в исследовательских данных; движок графа отношений в текущем ядре отсутствует.
3. Definition для существующего type-ID нельзя заменить: saveType требует новый ID при изменении определения/версии смысла. Исправления исследовательских определений относятся к ещё не опубликованному каталогу. Пять технических bootstrap-ID language/fitness/reading/work/rest не заменяются молча новым набором.
4. К каждой оси нужен конкретный valueKind и cardinality. Исследовательское «user-selected local value or text» не является допустимым enum. Смешанные значения из 102 исходных записей предварительно разнести по смыслу; не терять исходную подпись.
5. LOCAL_CHOICE требует реестр AxisValue с ID/версией. Для FREE_LABEL values должен быть пустым. customValuesAllowed не отдельное поле ядра: поведение добавления своего значения должно быть обеспечено явным действием и проверено.
6. Подсказки ActivityType ссылаются на ID осей/метрик без версии. При нескольких версиях нужен однозначный выбор актуального определения для нового ввода; существующая запись сохраняет свою версию. Нельзя считать, что подсказка автоматически решает выбор версии.
7. Составные количественные кандидаты («подходы/повторы/вес», «ночи/наблюдения/маршруты», «матч/раунд/задача») не импортируются одной метрикой. Сначала определить объект измерения, единицу, тип величины и допустимое объединение.
8. Все ссылки, единицы, родители и выбранные значения проверяются до импорта. Отчёт импорта должен оставаться доступным пользователю; отсутствие исключения не равно полному применению каталога.

## Границы количественной модели, выявленные при сопоставлении всех 20 кандидатов

| Потребность | Что возможно сейчас | Незакрытый смысл / проверка |
|---|---|---|
| Длительность | Вычисляется по сегментам, единственная активная линия | Не импортировать вторую SUM-метрику длительности и не считать незаписанное время бездействием |
| Расстояние, число повторов, подъём | SUM при явном SESSION/SEGMENT и подходящих единицах | Граница измерения должна быть ясна; одно измерение после деления времени не копируется на обе части |
| Величина всей сессии в коротком отчёте | Возвращается целиком, если соответствующая сессия попала в выборку | Это не величина внутри выбранного окна. Два дневных отчёта могут оба включить одно whole-session измерение; их суммы нельзя складывать без дедупликации и знания области |
| Скорость / темп | Можно хранить отдельными BY_TARGET метриками | Автоматического взвешенного среднего и обращения скорость↔темп нет. factorToBase поддерживает линейное масштабирование, не обратную зависимость. Нужны исходные расстояние и длительность с одинаковой областью |
| Вес по подходам | Можно сохранить одно значение каждого metric/version/unit на SESSION или SEGMENT | Вложенного target «подход» нет. Нельзя представить произвольную серию подходов с разными весами одной цифрой или искусственно умножить общий вес на повторы |
| Страницы, эпизоды, изделия | Можно хранить явное число на сессии/сегменте | Нет самостоятельного объекта книги/издания/эпизода/изделия как target. Позиция страницы, прочитанный объём и уникальные объекты требуют разного смысла |
| Партия/круг/пазл | Явный счётчик возможен | Нет отдельного реестра событий/объектов, исключающего повторный подсчёт одного события при нескольких сессиях |
| Субъективное усилие/оценка | BY_TARGET число возможно | Нужна определённая шкала. maxScale ограничивает дробность, а не минимум/максимум шкалы; поле диапазона в Metric отсутствует |
| Наблюдения природы | Число можно сохранить | Структурированная запись таксона/даты/места/вложений не представлена Metric; это предметная запись, не одна количественная ось |
| Статус задачи/повторяемость/маршрут | Свободные метки и локальные выборы доступны | Завершение, срок, расписание и идентичность маршрута не реализуются арифметическим SUM |

## Проверяемые условия будущей интеграции

- Один старт без категории и без осей; уточнение после старта не меняет фактическое начало.
- Однократный импорт полного согласованного пакета, повторный импорт, локально изменённые имена/родители, частичные конфликты и некорректные ссылки дают понятный воспроизводимый результат.
- Импорт не теряет ни одну исходную запись: каждое исходное qualified-ID имеет явное решение (сохранить/уточнить/сопоставить/историческая версия), а число итоговых узлов само по себе не является показателем полноты.
- Старые сегменты и значения остаются читаемыми после обновления каталога; новый смысл не присваивается старому ID автоматически.
- Дополнительная классификация/поисковая связь не создаёт второго времени.
- 5 км всей тренировки, пересекающей полночь, не превращаются в доказанные 5 км каждого дня. Два отчёта сообщают область величины явно.
- Темп 5 мин/км и скорость 12 км/ч не конвертируются линейным коэффициентом единиц; недопустимое преобразование не маскируется близким числом.
- Три подхода с разным весом не сводятся к одному значению без явного выбранного способа записи. Пока отсутствует подходящий target, сохраняется открытая потребность, а не ложная полнота.

## Остаток

Согласованный полный исследовательский каталог ещё собирается: поэлементная проверка ISCO, межраздельные связи и составные действия остаются открыты. Следом требуется конкретная схема переносимого пакета, сопоставление значений, решение о границе первого интеграционного изменения и передача Astra в существующую облачную задачу. Этот документ не запускает новую разработку и не фиксирует дизайн интерфейса за пользователя и Opus.
